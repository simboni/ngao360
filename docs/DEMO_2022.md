# 2022 Bungoma historical demo

A separate demo organisation that shows the full NGAO TALLY chain on a 2022 setting: registry, intake,
capture, two-person verification, constituency and county collation, holding cases, an immutable snapshot and
exports. It sits beside the synthetic `demo` organisation and never mixes with it.

> **Every screen, snapshot and export of this organisation shows two labels:** the existing unofficial
> wording ("Parallel tally — not an official IEBC result" and the full disclaimer) **and**
> **HISTORICAL DEMO / SIMULATED DATA**. Nothing in it is an official result. Station-level governor
> figures are always simulated. Do not present any figure from this demo as a real 2022 result for a real
> person or polling station.

Background: [DATA_SOURCES_2022.md](./DATA_SOURCES_2022.md) (what is public and the legal notes),
[DECISIONS.md](./DECISIONS.md) (2022 data allowed for the demo, labelled historical; synthetic data for
tests).

## 1. What is real and what is simulated

| Item | Status | Where it comes from |
| --- | --- | --- |
| County name and number (Bungoma, 39) | Real, public | Constitution of Kenya, 2010, First Schedule (`county.name` is `verified: true`) |
| `039` as the first 3 digits of IEBC station codes | Inferred | 34A file-name pattern (`county.code` is `verified: false`) |
| 9 constituencies and 45 ward names | Public, but not checked offline in this build | `boundaries` block, `verified: false`. Check them against the IEBC list or the MIT boundary list before relying on them |
| Constituency (3-digit) and ward (4-digit) codes | **Placeholders** (numbered in list order) | `codes` block, `verified: false`. Not the IEBC codes |
| Polling centres, streams, station codes, registered voters per station | **Simulated** | Generated from the seed; codes follow the inferred 15-digit pattern county(3) + constituency(3) + ward(4) + centre(3) + station(2) |
| County governor totals per candidate, rejected votes, registered voters | **UNVERIFIED placeholders** until you plug in the gazetted figures | `governor` block of the config |
| Candidate names | Neutral labels ("Candidate A (simulated)") | Real names only when you supply verified names **and** verified totals (section 4) |
| 37A station figures, 37B constituency figures, form images | **Simulated** | Generated so that station sums equal the configured constituency and county totals exactly |
| Users, reviewers, timing, discrepancies | **Synthetic** | Demo users `@<slug>.example.org` |
| 34A presidential scans | Real only if **you** import local copies you are allowed to use | `pnpm demo:import-34a` (section 5) |

The data model carries this on the cycle: `dataProvenance = HISTORICAL_DEMO`, `containsSimulatedData = true`
and `provenanceNotes`; the organisation is marked `historical_demo`. Database triggers refuse to remove these
labels, also for the owner role.

## 2. Run it

```bash
set -a; . ./.env; set +a          # DATABASE_URL (owner, for provisioning), APP_DATABASE_URL, MFA key
pnpm db:migrate
pnpm demo:2022-bungoma            # builds the API, then creates or refreshes the demo (about 2 minutes)
```

Options: `--config <path>` (default `data/demo-2022/bungoma.config.json`), `--tenant <slug>` (default
`bungoma-2022-demo`), `--concurrency <n>`. The command is idempotent: a second run with the same simulated
layer changes nothing (same deterministic idempotency keys, same registry version, one snapshot). It never
fetches anything from the network.

Two safety rules:

- `--tenant` only ever creates a **new** organisation or refreshes one that is already a historical demo. If the
  slug belongs to an ordinary organisation the command stops without touching it (no relabel, rename,
  synthetic owner accounts or cycle), because the demo label can never be removed again and the demo users
  share a known password.
- An organisation is built from **one** simulated layer. If the config now gives a different layer (another
  seed, figures, constituencies or wards, simulation settings or candidate names shown on the ballot), the
  command refuses and asks for a new `--tenant`, instead of keeping the old figures under a new registry.
  Editing only source strings, notes or `verified` flags keeps the same layer (they are left out of the
  layer fingerprint), so documenting a source never forces a rebuild. With `SEED_DEMO_MFA=preenrolled` (development only) privileged demo users get the shared development
TOTP secret, as with `pnpm db:seed`.

What it does:

1. Provisions the organisation `bungoma-2022-demo` (marked historical demo), its system roles and 11 synthetic
   users (`owner@`, `registrar@`, `legal@`, `clerk1-3@`, `verifier1-3@`, `supervisor@`, `supervisor2@`, all
   `@bungoma-2022-demo.example.org`, password `SEED_DEMO_PASSWORD`). Like the seed, this one step runs as the
   schema owner because there is no tenant-provisioning API.
2. Everything else goes through the API services as those users, with the same permission checks:
   - the `HISTORICAL_DEMO` cycle with the simulated flag and provenance notes;
   - the generated registry, imported by `registrar@` and approved by `owner@` (the existing maker-checker
     rule; the importer can never approve their own import);
   - constituency and county tally centres, the governor contest (neutral labels) and a presidential contest
     for imported 34A scans;
   - 34A–34C and 37A–37C templates created by `registrar@` and approved by `legal@`;
   - simulated 37A forms (PNG images with a SIMULATED banner and watermark) uploaded by a clerk, captured and
     verified by a different verifier. By the config's `workflow` block about 5 % of stations stay missing,
     7 % wait for second review and 2 stations are keyed with a wrong total, so an arithmetic discrepancy case
     holds them;
   - verified 37B forms for each constituency and a 37C for the county (equal to the config totals). Because
     coverage is incomplete, the cross-stage comparison opens low-severity variance cases, as it should;
   - one immutable snapshot by `supervisor@`.

Sign in at http://localhost:3000 with organisation code `bungoma-2022-demo`, for example as `supervisor@…` to
see **Parallel tally** (coverage, missing never zero, holding cases), or as `verifier1@…` to see the review
queue. The red banner under the top bar appears on every screen.

## 3. The config file

`data/demo-2022/bungoma.config.json` is validated by `parseDemoConfig` (`packages/shared/src/demo-2022/config.ts`).
Every real-world value is `{ "value": …, "source": "…", "verified": false }`. The loader refuses to run when:

- a value claims `verified: true` without a real source string (empty, or containing words such as
  UNVERIFIED, PLACEHOLDER, TODO or INFERRED);
- a candidate has a real `name` that is not `verified: true`, or any candidate total is unverified while a real
  name is given;
- a candidate without a verified name has a label that does not say "(simulated)";
- votes cast exceed registered voters, or county turnout exceeds the simulated station maximum;
- `constituencyTotals` (optional) do not add up to the county totals, candidate by candidate and for rejected
  votes.

`simulation` controls the generator: registered voters per station (min / max / mean), streams per centre,
turnout bounds and the workflow shares. `dataset.seed` fixes the simulated layer; change it for a different
one (in a new organisation: pass a new `--tenant`). `constituencyTotals` must name every configured
constituency exactly once (duplicates are refused). The generator (`generateGovernorLayer`) uses capped largest-remainder allocation, so station sums equal
the totals exactly, no station records more votes cast than `registered × turnout.max`, and the result is
deterministic for a seed (property tests in `packages/shared/src/demo-2022/demo-2022.test.ts`).

## 4. Plug in verified gazetted totals

1. Find the official county governor result for Bungoma in the Kenya Gazette (the notice of about
   23 August 2022 listing governors-elect; check whether it gives every candidate's votes) or another
   official IEBC publication. Keep the exact reference.
2. For each candidate, set `votes.value` and `votes.source` (for example
   `"Kenya Gazette Vol. CXXIV No. …, Gazette Notice No. …, 2022, p. …"`) and `votes.verified: true`. Do the
   same for `rejected` and `registeredVoters`.
3. Only once every total is verified, you may add real names: `"name": { "value": "<as gazetted>",
   "source": "<same notice>", "verified": true }` and `partyLabel`. Station-level figures stay SIMULATED and
   labelled so.
4. If you have verified constituency totals (for example from scanned 37B copies you are allowed to use), add
   them under `constituencyTotals` with their source.
5. If you know the real IEBC constituency and ward codes (they appear inside the 34A file names), replace the
   placeholder codes and set `codes.verified: true` with the source. Only the county, constituency and ward
   segments of the generated station codes can then match real codes: the polling-centre and stream segments
   are generated (centres counted from 001 per ward, stream counts drawn at random), so a real 15-digit
   station code matches a generated one only by coincidence. Real 34A scans therefore still go to a draft
   registry version (now under the right constituency and ward), which a different person approves.
6. Run `pnpm demo:2022-bungoma --tenant <new slug>`. Changing totals, names, codes or wards changes the
   simulated layer, and the command refuses to rebuild an existing demo organisation from a different layer
   (earlier submissions are kept and never rewritten). Adding only sources and `verified: true` to unchanged
   figures keeps the layer, so a re-run on the same organisation is still a no-op.

## 5. Import local 34A scans (legally)

Before you use any real scan:

- **Written permission from IEBC** for any commercial or public demo (Copyright Act s. 25; see
  DATA_SOURCES_2022.md). Credit the source and do not use the IEBC logo in a way that implies endorsement.
- **Redact names and signatures** of presiding officers and agents before any image is shown (Data Protection
  Act 2019).
- **Do not use the crowdsourced ib0b CSV** (`forms-export.csv`): it has no licence and is marked "education
  purposes only". This build never reads it.
- Use only copies you obtained lawfully. The tool works on a local directory and never downloads anything.

```bash
pnpm demo:import-34a --dir ~/scans/bungoma-34a --tenant bungoma-2022-demo --dry-run   # report only
pnpm demo:import-34a --dir ~/scans/bungoma-34a --tenant bungoma-2022-demo             # import
```

Options: `--as <email>` (submitter with `tally.submit`, default `clerk1@`), `--registrar <email>` (creates the
draft registry version, default `registrar@`), `--cycle <name>`, `--redacted`, `--json`.

- File names must follow `1_34_A_<15-digit station code>_<KIEMS serial>_<YYYYMMDD>_<HHMMSS>.<ext>` (case and
  `_ - . space` separators are tolerated). Unparsable names are listed with the reason and skipped.
- The importer works only in an organisation marked as a historical demo, in its `HISTORICAL_DEMO` cycle, and
  acts only as that organisation's synthetic demo users (`…@<slug>.example.org`); it refuses anything else.
- Station codes whose county segment is not the demo registry's county (039 for Bungoma) are listed under
  "other county" and skipped; they are never filed under this county's constituencies and wards.
- Station codes found in the approved registry are imported through the normal intake (SHA-256, immutable
  storage, duplicate detection) as presidential 34A submissions with source type "copy of publicly published
  form". A second, different scan of the same station is flagged as a possible duplicate, never dropped.
- Unknown station codes go into a **draft** registry version (approved stations plus the new codes, names
  marked unverified). The importer never approves it: a different person with `reference.approve` reviews and
  approves it in **Reference data → Station registry**, then a re-run imports the waiting files.
- **Every** image is stored with a **"not for display until redacted"** hold in the same transaction as the
  file, whatever the flags. The viewer refuses to show it (`NOT_FOR_DISPLAY_UNTIL_REDACTED`). To attach a
  redacted copy made outside the platform (blur names and signatures; keep figures legible):

  ```bash
  pnpm demo:redact-34a --tenant bungoma-2022-demo --submission SUB-2022-000123 --file redacted.png --reason "Names and signatures blurred"
  ```

- `--redacted` does not skip the hold. It records the operator's declaration that the files are already
  redacted (audit event `file.display_hold.redaction_declared`, naming the declarer) and marks the hold as
  declared. A different person then checks the scan and confirms:

  ```bash
  pnpm demo:redact-34a --tenant bungoma-2022-demo --submission SUB-2022-000123 --confirm-declared --reason "Checked: no names or signatures visible"
  ```

  The server stores a re-encoded copy without metadata as the displayable copy (PDFs need `--file`).
- Releasing a hold needs `tally.approve` (default `supervisor@`) and is refused for the person who imported
  the scan or declared it redacted. The release is audited with the reviewer and the reason; the copy is
  stored with its own SHA-256 and served from then on; the original is never altered or shown. Written IEBC
  permission (item 5 of docs/QUESTIONS.md) is still needed before any real scan is shown.
- Re-running the import is safe: files already imported are reported as such and nothing is duplicated.

Capturing presidential figures needs the candidate list. The config has none (`presidential.candidates`);
add the published ballot names with their source before capturing, or add them through the contest screen.

## 6. Tests

All tests use synthetic files only:

- `packages/shared/src/demo-2022/demo-2022.test.ts`: config loader rules, 34A file names, allocation and
  property tests of the generator (exact sums, no negative or over-registered values, determinism).
- `apps/api/test/demo-2022.e2e.spec.ts`: the demo at small scale with `fixtures/demo-2022/bungoma-small.config.json`:
  maker-checker registry, distinct verifiers, parallel tally equal to the generated figures for the verified
  share, 37B/37C equal to the config, holding cases, labels on `/auth/me`, the snapshot and exports, labels
  cannot be removed, idempotent re-run; an ordinary organisation is never taken over via `--tenant`, a
  different simulated layer is refused, non-synthetic accounts are refused, and the audit-log CSV carries
  both labels.
- `apps/api/test/demo-34a-import.integration.spec.ts`: dry run, real run, re-run, draft registry for unknown
  codes, maker-checker approval, display hold and redacted copy, `--redacted` still held until a second
  person confirms, other-county codes skipped, non-demo organisations refused, against `fixtures/demo-2022/34a`
  (regenerate with `pnpm fixtures:demo-2022`).
- `apps/api/src/modules/tally/export/export.spec.ts` and `packages/shared/src/provenance.test.ts`: every
  export format of a labelled dataset carries both labels.

Run them with `set -a; . ./.env; set +a; pnpm test`, or only these with `pnpm test:demo-2022`.
